# Recall@K — объяснение с нуля

## 1. Зачем нужна Recall@K

Представим поисковик картинок Greenterest.

По прошлой истории мы знаем, на какие изображения пользователь кликнул. Для учебной задачи считаем:

```text
label = 1 -> картинка релевантна / пользователь кликнул
label = 0 -> картинка нерелевантна / пользователь не кликнул
```

Новая модель каждой картинке даёт `score`:

```text
чем score выше, тем выше картинка должна стоять в выдаче
```

Пользователь обычно видит только первые несколько результатов. Поэтому нас интересует не качество по всем объектам сразу, а качество первых `K` позиций.

**Recall@K отвечает:**

> Из всех действительно релевантных картинок какую долю модель успела поместить в первые K позиций?

---

## 2. Что означают labels и scores

```python
labels = [1, 0, 1, 0, 1]
scores = [0.90, 0.80, 0.20, 0.70, 0.60]
```

Каждая позиция относится к одному объекту:

| объект | label | score |
|---|---:|---:|
| A | 1 | 0.90 |
| B | 0 | 0.80 |
| C | 1 | 0.20 |
| D | 0 | 0.70 |
| E | 1 | 0.60 |

`label` — исторический факт.

`score` — предсказание новой модели.

Нельзя отдельно сортировать `labels` и `scores`: тогда связь между объектом и его таргетом потеряется.

---

## 3. Что такое `@K`

`Recall@3` означает:

1. отсортировать объекты по `score` по убыванию;
2. взять первые 3;
3. посмотреть, сколько среди них реальных positive;
4. сравнить с количеством всех positive.

Для примера выше ranking такой:

| rank | объект | label | score |
|---:|---|---:|---:|
| 1 | A | 1 | 0.90 |
| 2 | B | 0 | 0.80 |
| 3 | D | 0 | 0.70 |
| 4 | E | 1 | 0.60 |
| 5 | C | 1 | 0.20 |

Top-3:

```text
A, B, D
labels -> [1, 0, 0]
```

Всего positive:

```text
A, C, E -> 3
```

В Top-3 positive:

```text
A -> 1
```

Значит:

\[
Recall@3 = 1/3 pprox 0.333
\]

---

## 4. Связь с обычным Recall

В бинарной классификации:

\[
Recall = TP / (TP + FN)
\]

Где:

- `TP` — positive, который модель выбрала;
- `FN` — positive, который модель не выбрала.

В ranking-задаче удобно считать:

```text
Top-K          -> predicted positive
ниже Top-K     -> predicted negative
```

Поэтому:

\[
Recall@K = TP@K / (TP@K + FN@K)
\]

Так как `TP + FN` — это все реальные positive, можно запомнить проще:

\[
Recall@K =
rac{positive\ в\ Top-K}{positive\ во\ всём\ наборе}
\]

---

## 5. Интуиция, которую стоит запомнить

**Recall = охват.**

Самый короткий вопрос:

> Сколько всего хорошего мы нашли?

Если всего было 10 релевантных картинок, а в Top-20 попало 8:

```text
TP = 8
FN = 2
```

\[
Recall@20 = 8/(8+2)=0.8
\]

То есть модель нашла 80% всего релевантного.

---

## 6. Почему нельзя просто увеличить K до бесконечности

Если `K` равен количеству всех объектов, то все positive обязательно попадут внутрь Top-K:

```text
Recall@N = 1
```

если positive вообще существуют.

Но такой результат не означает хорошее ранжирование. Поисковик, который говорит:

> Вот 100 000 результатов, нужное где-то здесь

не является хорошим поиском.

Поэтому K выбирают исходя из продукта:

```text
Recall@5
Recall@10
Recall@20
Recall@100
```

---

## 7. Пример хорошего Recall

```python
labels = [1, 0, 1, 0, 1]
scores = [0.99, 0.10, 0.95, 0.20, 0.90]
k = 3
```

Top-3 labels:

```text
[1, 1, 1]
```

Всего positive = 3.

В Top-3 positive = 3.

\[
Recall@3 = 3/3 = 1
\]

Модель поместила все релевантные объекты в первые три позиции.

---

## 8. Реализация на Python

Прозрачный вариант через индексы:

```python
from typing import List


def recall_at_k(labels: List[int], scores: List[float], k=5) -> float:
    ranked_indices = sorted(
        range(len(scores)),
        key=lambda i: scores[i],
        reverse=True,
    )

    top_k_indices = ranked_indices[:k]

    true_positives = sum(labels[i] for i in top_k_indices)
    all_positives = sum(labels)

    if all_positives == 0:
        return 0.0

    return true_positives / all_positives
```

Вариант через пары:

```python
def recall_at_k(labels, scores, k=5):
    ranked = sorted(
        zip(scores, labels),
        key=lambda pair: pair[0],
        reverse=True,
    )

    top_k = ranked[:k]
    tp = sum(label for _, label in top_k)
    positives = sum(labels)

    if positives == 0:
        return 0.0

    return tp / positives
```

---

## 9. Почему `tp / k` — это не Recall

Если написать:

```python
tp / k
```

то вопрос будет:

> Какая доля Top-K релевантна?

Это уже **Precision@K**.

Recall делится не на K, а на количество **всех реальных positive**.

Пример:

```text
Всего positive = 10
K = 5
В Top-5 positive = 4
```

Recall:

\[
4/10 = 0.4
\]

Precision:

\[
4/5 = 0.8
\]

Один ranking может одновременно иметь высокий Precision и низкий Recall.

---

## 10. Recall@K vs Precision@K

### Recall@K

> Из всех relevant сколько попало в Top-K?

\[
TP/(TP+FN)
\]

### Precision@K

> Из Top-K сколько relevant?

\[
TP/(TP+FP)
\]

Запоминалка:

```text
Recall    -> охват всего хорошего
Precision -> чистота выбранного Top-K
```

---

## 11. Что происходит с Recall при росте K

Для фиксированного ranking:

```text
Recall@1 <= Recall@2 <= Recall@3 <= ...
```

Recall@K **не может уменьшаться**.

Почему:

- Top-(K+1) содержит весь Top-K;
- уже найденные positive не исчезают;
- новый объект либо добавит ещё один TP, либо ничего не изменит.

Это частый вопрос на собеседовании.

## 12. Edge cases

### Нет positive

```python
labels = [0, 0, 0]
```

Формально:

\[
Recall = 0/0
\]

Метрика математически не определена. В учебных задачах часто возвращают `0.0`, но в реальных системах возможны другие соглашения: пропуск query, `NaN`, отдельная политика.

### `k > n`

Python slice безопасен:

```python
ranked[:k]
```

вернёт все доступные объекты.

### `k = 0`

Top-0 пустой. При наличии positive Recall будет `0.0`. В production API часто разумнее запрещать `k <= 0`.

### Разная длина списков

```python
len(labels) != len(scores)
```

логически некорректно: каждому объекту нужен и label, и score.

### Равные scores

Ranking между tied-объектами должен иметь договорённое правило. Python `sorted` стабилен и сохраняет исходный порядок при равных ключах.

## 13. Мини-тесты

```python
assert recall_at_k(
    labels=[1, 0, 1],
    scores=[0.9, 0.8, 0.7],
    k=2,
) == 0.5
```

Top-2:

```text
[1, 0]
```

Всего positive = 2, найден 1.

Ещё:

```python
assert recall_at_k(
    labels=[1, 1, 0],
    scores=[0.9, 0.8, 0.1],
    k=2,
) == 1.0
```

## 14. Типичные ошибки

### Ошибка 1 — взять первые K исходного labels

```python
labels[:k]
```

Нужно сначала отсортировать по `scores`.

### Ошибка 2 — сортировать labels

```python
sorted(labels, reverse=True)
```

Это разрушает соответствие label-score.

### Ошибка 3 — использовать threshold

```python
score >= 0.5
```

В этой задаче predicted positive задаются через Top-K, а не threshold.

### Ошибка 4 — делить на K

Это Precision@K.

### Ошибка 5 — смотреть только на Top-K и забыть positives ниже K

Именно они являются `FN` и снижают Recall.

---

## 15. Когда Recall особенно важен

Recall критичен, когда дорого **пропустить** relevant объект.

Примеры:

- candidate generation в recommendation;
- первый этап document retrieval;
- поиск потенциальных fraud cases;
- screening;
- поиск подходящих вакансий.

В двухэтапной системе:

```text
1. Retriever выбирает 1000 кандидатов
2. Reranker переставляет эти 1000
```

Если нужный документ не попал на первом этапе, reranker уже не сможет его вернуть. Поэтому candidate retrieval часто оптимизируют на высокий Recall.

---

## 16. Ограничение Recall@K

Recall@K не учитывает точную позицию внутри Top-K.

Для K=5:

```text
A: R R R N N
B: N N R R R
```

Если число relevant одинаково, Recall@5 одинаков.

Но пользователь может предпочесть A, потому что хорошие результаты стоят выше.

Для учёта позиции используют, например:

- NDCG@K;
- MRR;
- MAP.

## 17. Вопросы на собеседовании

### 1. Что такое Recall@K?

Доля всех relevant объектов, попавших в первые K позиций ranking-а.

### 2. Формула?

\[
Recall@K = TP/(TP+FN)
\]

### 3. Чем отличается от Precision@K?

Recall нормируется на все actual positives, Precision — на predicted positives / Top-K.

### 4. Почему Recall@K обычно растёт с K?

Потому что расширение Top-K не удаляет ранее найденные positives.

### 5. Может Recall@K = 1 при плохом Precision?

Да.

```text
2 relevant всего
K = 100
обе relevant в Top-100
```

Recall = 1, Precision = 0.02.

### 6. Может Precision@5 = 1 при Recall@5 = 0.05?

Да, если всего 100 relevant, а все 5 Top-5 релевантны.

### 7. Что делать, если positive отсутствуют?

Сначала сказать, что формула не определена из-за нулевого знаменателя, затем уточнить принятую в проекте конвенцию.

### 8. Почему Recall важен в candidate generation?

Потому что не найденный кандидатом объект нельзя восстановить следующим reranking-этапом.

## 18. Похожие задачи на собеседовании

### Задача A

```text
labels = [1, 0, 1, 1, 0]
scores = [0.3, 0.9, 0.8, 0.1, 0.7]
K = 3
```

Ranking:

```text
0.9 -> 0
0.8 -> 1
0.7 -> 0
0.3 -> 1
0.1 -> 1
```

Top-3 positive = 1.

Всего positive = 3.

\[
Recall@3 = 1/3
\]

### Задача B

Модель A:

```text
Recall@20 = 0.92
Precision@20 = 0.15
```

Модель B:

```text
Recall@20 = 0.70
Precision@20 = 0.60
```

Какая лучше?

Без продуктовой цели ответить нельзя. Для candidate generation A может быть предпочтительнее; для конечной SERP низкий Precision A может быть неприемлем.

### Задача C

Почему нельзя честно сравнивать Recall@10 одной модели и Recall@100 другой?

Потому что бюджет K различается. При большем K найти positive легче.

```text
Recall = "сколько хорошего нашли"

Recall@K =
positive в Top-K
-----------------
positive вообще
```

Confusion matrix:

```text
Recall = TP / (TP + FN)
```

## 20. Связь с заданием курса

Общий алгоритм:

```text
1. labels и scores относятся к одним объектам.
2. Сортируем объекты по score по убыванию.
3. Первые K считаем predicted positive.
4. Всё ниже K считаем predicted negative.
5. Для Recall считаем TP и FN.
6. Возвращаем TP / (TP + FN).
```

Перед автопроверкой проверь:

- имя функции точно `recall_at_k`;
- аргументы совпадают с шаблоном;
- сортировка по `scores`;
- сортировка по убыванию;
- связь score-label не теряется;
- возвращается `float`;
- обработан нулевой знаменатель согласно ожидаемому контракту.
