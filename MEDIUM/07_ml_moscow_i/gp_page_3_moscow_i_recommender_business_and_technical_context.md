# 1. Что произошло в продукте

В маркетплейсе KarpovExpress работает блок рекомендаций:

```text
«Вместе с этим товаром часто берут»
```

Пользователь находится на странице конкретного товара. Например, он смотрит беспроводные наушники. Система должна показать четыре других товара:

- чехол;
- зарядное устройство;
- амбушюры;
- переходник.

Но иногда в блоке снова показываются те же самые наушники.

Это называется self-recommendation:

```text
current_item_id == recommended_item_id
```

---

# 2. Почему это бизнесовая проблема

В блоке всего четыре карточки. Если одна карточка занята текущим товаром:

```text
1 / 4 = 25%
```

Четверть recommendation inventory расходуется впустую.

Возможные последствия:

- пользователь получает меньше полезных вариантов;
- снижается вероятность клика;
- снижается cross-sell;
- снижается add-to-cart;
- теряется потенциальный GMV;
- ухудшается восприятие качества продукта;
- растёт число жалоб;
- пользователь считает систему «глупой».

Даже если ошибка встречается не всегда, команда обязана понять её частоту и быстро убрать.

---

# 3. Как работает item-to-item система

Item-to-item рекомендация отвечает на вопрос:

> Какие товары обычно связаны с текущим товаром?

Связь может строиться по:

- совместным просмотрам;
- совместным покупкам;
- совместному добавлению в корзину;
- последовательности действий;
- similarity embeddings;
- похожести атрибутов.

Пример корректных связей:

```text
ноутбук → мышь
ноутбук → сумка
ноутбук → подставка
```

Пример ошибки:

```text
ноутбук → ноутбук
```

# 4. Возможные причины self-recommendation

## 4.1. Self-pairs в обучающих данных

При генерации пар могли забыть условие:

```text
item_i != item_j
```

Например, в истории:

```text
[A, A, B]
```

наивный pipeline создаёт пары:

```text
A → A
A → B
B → A
```

## 4.2. Повторные события

Пользователь несколько раз открыл одну карточку:

```text
A, A, A, B
```

Если co-view считается без дедупликации, A становится сильным соседом самого себя.

## 4.3. Отсутствие post-processing фильтра

Модель может вернуть current item, а serving layer не удаляет его перед отправкой клиенту.

## 4.4. Несогласованные идентификаторы

Один физический товар может иметь:

- product_id;
- SKU;
- offer_id;
- variant_id;
- parent_product_id.

Технически ID различаются, но пользователь видит тот же товар.

## 4.5. Fallback

Если модель вернула мало кандидатов, fallback популярных товаров может случайно добавить current item.

## 4.6. Merge нескольких candidate sources

Final list может собираться из:

- co-buy;
- similar items;
- popularity;
- sponsored items.

После объединения могла не сработать дедупликация.

## 4.7. Кэш

Кэш мог использовать неправильный ключ или старый mapping товаров.

# 5. Как сформулировать недельную цель

Сильная формулировка:

> К концу недели текущий товар не отображается в собственном recommendation block, команда знает масштаб исходной проблемы и проверила влияние исправления на продуктовые метрики.

В этой цели три части:

```text
Measure → Fix → Validate
```

По-русски:

```text
Измерить → Исправить → Проверить
```

---

# 6. Почему Must Have должно быть три

В условии:

```text
каждая задача занимает один день
```

Рабочая неделя:

```text
5 дней
```

Правило MoSCoW:

```text
60% времени → Must Have
```

Расчёт:

```text
5 × 0.60 = 3 дня
```

Следовательно, нужно выбрать три Must Have задачи.

---

# 7. Первый Must: измерить масштаб

Нужно посчитать долю recommendation requests, где current item попал в final list.

Метрика:

\[
SelfRecommendationRate =
\frac{\text{показы с current item внутри рекомендаций}}
{\text{все показы recommendation block}}
\]

Важно считать именно на уровне показа блока. Если в одном блоке current item встретился дважды, это всё равно один затронутый показ, но дополнительно можно считать число ошибочных позиций.

Полезные разрезы:

- категория;
- товар;
- регион;
- устройство;
- версия приложения;
- source candidate generator;
- позиция в блоке;
- fallback;
- модель;
- дата и час.

Без baseline команда не знает:

- редкая это ошибка или массовая;
- где она возникает;
- сколько recommendation inventory теряется;
- насколько fix помог.

---

# 8. Второй Must: deterministic hotfix

Нужно добавить обязательный фильтр:

```text
recommended_item_id != current_item_id
```

Упрощённая логика:

```python
filtered_items = [
    item
    for item in recommended_items
    if item != current_item
]
```

Но production-реализация должна учитывать:

- варианты одного товара;
- parent-child mapping;
- разные offer одного SKU;
- дубли;
- необходимость заполнить освободившийся слот.

## 8.1. Почему это надёжнее одного переобучения

Hotfix работает на final output. Даже если модель, fallback или cache снова вернули current item, post-processing не пропустит его пользователю.

Переобучение не гарантирует этого, потому что ошибка может находиться не только в train data.

---

# 9. Третий Must: A/B-тест

Исправление меняет состав выдачи. Освободившийся слот будет заполнен другим кандидатом. Нужно проверить, что новый список действительно полезнее.

## Контроль

Текущая логика.

## Тест

Current item удаляется, а на его место берётся следующий допустимый кандидат.

## Техническая primary metric

```text
SelfRecommendationRate
```

Она должна стать нулевой или практически нулевой.

## Продуктовые метрики

- recommendation CTR;
- add-to-cart rate;
- purchase conversion;
- GMV per impression;
- revenue per impression;
- клики по recommendation block.

## Guardrails

- latency;
- error rate;
- empty-slot rate;
- coverage;
- duplicate rate;
- out-of-stock rate.

В условии специально указано, что A/B-платформа уже есть и тесты быстрые. Поэтому валидация доступна по низкой цене.

---

# 10. Почему прошлый A/B-тест не поймал проблему

A/B-тест отвечает только на вопросы, для которых заданы метрики.

Прошлый тест мог смотреть на:

- CTR;
- conversion;
- GMV;
- revenue.

Self-recommendation могла:

- возникать редко;
- быть размазана по трафику;
- не иметь отдельного guardrail;
- компенсироваться улучшениями в других случаях.

Поэтому:

```text
эксперимент успешен
```

не означает:

```text
локальных дефектов нет.
```

---

# 11. Почему жалобы важны, но недостаточны

Жалобы показывают:

- пользователи заметили проблему;
- проблема влияет на восприятие;
- автоматические метрики имеют слепую зону.

Но жалобы не дают частоту. Нельзя понять, затронуто 0.01% или 20% показов.

Правильная цепочка:

```text
жалоба
→ гипотеза
→ измерение
→ исправление
→ эксперимент
→ постоянный мониторинг
```

---

# 12. Почему не нужно сразу менять модель

Плохое мышление:

```text
В ML-продукте появилась ошибка.
Значит, нужна новая ML-модель.
```

Сильное мышление:

```text
Можно ли гарантированно убрать дефект простым правилом?
Как измерить его масштаб?
Как проверить продуктовый эффект?
Нужно ли вообще менять алгоритм?
```

В этой задаче проблема решается на product policy и serving layer.

---

# 13. Правильная архитектура post-processing

Рекомендательная система должна выглядеть не так:

```text
модель → пользователь
```

а так:

```text
candidate generation
→ ranking
→ remove current item
→ deduplicate
→ remove unavailable items
→ policy filters
→ fallback
→ final recommendations
```

Примеры обязательных фильтров:

- current item exclusion;
- duplicate exclusion;
- availability;
- legal restrictions;
- возрастные ограничения;
- региональная доступность;
- inventory;
- заблокированные товары.

Модель предлагает кандидатов, но final output обязан соблюдать продуктовые инварианты.

---

# 14. Acceptance criteria hotfix

1. Current item отсутствует во всех final recommendation lists.
2. SelfRecommendationRate равен нулю или технически близок к нулю.
3. В блоке по возможности остаётся четыре карточки.
4. Освободившийся слот заполняется следующим кандидатом.
5. Нет значимого роста latency.
6. Нет роста error rate.
7. Нет ухудшения CTR, conversion и GMV выше согласованного порога.
8. Правило работает для SKU, offers и variants.

---

# 15. Главный вывод

Минимальный законченный цикл недели:

```text
1 день — измерить self-recommendation rate
1 день — внедрить deterministic hotfix
1 день — провести A/B-тест
```

Это быстрее, надёжнее и дешевле, чем полная замена модели или архитектуры.
