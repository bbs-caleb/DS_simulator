# MOSCOW I — страница 2
# Time Boxing, правило 60–20–20 и управление неопределённостью

# 1. Зачем MoSCoW связывают со временем

MoSCoW — не только способ расставить задачи по важности. Это ещё и способ распределить ограниченный бюджет:

- времени;
- людей;
- внимания;
- вычислений;
- организационной энергии.

Команда должна решить не только, что является Must, Should и Could, но и сколько времени она готова обещать на каждую категорию.

---

# 2. Что такое Time Boxing

Time Boxing — это подход, при котором под задачу заранее выделяется ограниченный временной блок.

Плохая формулировка:

```text
Будем анализировать ошибки, пока не разберёмся полностью.
```

Хорошая формулировка:

```text
В четверг за один рабочий день разбираем 100 False Negative,
создаём taxonomy ошибок и формулируем три гипотезы улучшения.
```

Хороший time box содержит:

1. конкретную цель;
2. начало;
3. окончание;
4. ожидаемый артефакт;
5. критерий остановки;
6. следующее решение после завершения времени.

Time Boxing особенно важен в ML, потому что эксперименты можно продолжать бесконечно:

- ещё одна модель;
- ещё один параметр;
- ещё один признак;
- ещё один split;
- ещё один способ калибровки.

Без ограничения времени исследование легко превращается в бесконечный процесс без доставки ценности.

---

# 3. Почему нельзя занять Must Have всю неделю

Представим пятидневную неделю. Команда объявила обязательными пять задач, каждая занимает один день.

На бумаге:

```text
5 дней работы = 5 дней обязательств
```

Но в реальном проекте возникают неожиданности:

- нет production-доступа;
- изменилась схема данных;
- service owner недоступен;
- тесты упали;
- библиотека несовместима;
- модель потребляет больше RAM;
- code review задержался;
- появился блокирующий bug;
- оценка задачи была слишком оптимистичной.

Если буфера нет, любое отклонение означает нарушение обещаний.

Такой план хрупок.

---

# 4. Буфер как запас прочности

MoSCoW предлагает не обещать весь доступный бюджет.

Should Have и Could Have выполняют роль управляемого буфера:

```text
если Must задержался,
сначала переносим Could,
затем при необходимости Should.
```

Это не безделье и не пустой резерв. Это способ защитить обязательный результат от неопределённости.

---

# 5. Правило 60–20–20

Рекомендуемое распределение:

| Категория | Доля времени |
|---|---:|
| Must Have | 60% |
| Should Have | 20% |
| Could Have | 20% |

Для рабочей недели из пяти дней:

```text
5 × 60% = 3 дня Must Have
5 × 20% = 1 день Should Have
5 × 20% = 1 день Could Have
```

Типовой план:

| День | Категория |
|---|---|
| Понедельник | Must Have |
| Вторник | Must Have |
| Среда | Must Have |
| Четверг | Should Have |
| Пятница | Could Have |

---

# 6. Как Should и Could поглощают ошибки оценки

Исходный план:

```text
Must   = 3 дня
Should = 1 день
Could  = 1 день
```

## Сценарий A: Must занял 4 дня

```text
4 дня Must
1 день Should
0 дней Could
```

Жертвуем Could, но обязательство выполнено.

## Сценарий B: Must занял 5 дней

```text
5 дней Must
0 дней Should
0 дней Could
```

Жертвуем Should и Could, но сохраняем главный результат.

## Сценарий C: Must занял 2 дня

```text
2 дня Must
1 день Should
2 дня Could
```

Появляется дополнительный бюджет на улучшения.

## Сценарий D: Should занял 2 дня

```text
3 дня Must
2 дня Should
0 дней Could
```

Could снова выступает резервом.

---

# 7. Ошибка оценки в процентах

Пусть Must Have оценён в три дня.

## Недооценка на 20%

```text
3 × 1.20 = 3.6 дня
```

Практически задача займёт около четырёх дней. План всё ещё выдерживает это за счёт Could.

## Недооценка на 50%

```text
3 × 1.50 = 4.5 дня
```

Must займёт почти всю неделю. Should и Could будут пожертвованы, но главное обязательство ещё можно завершить.

## Если Must не помещается даже в пять дней

Это сигнал, что команда плохо понимала задачу. Возможные причины:

- нет декомпозиции;
- пропущены зависимости;
- не проведён discovery;
- задача слишком крупная;
- оценка была политической;
- не учтены согласования;
- отсутствует технический spike.

---

# 8. Недельный план антиспам-проекта

В официальном примере:

```text
Понедельник–среда → деплой
Четверг           → анализ ошибок
Пятница           → градиентный бустинг
```

## Почему деплою выделено три дня

Даже простая модель требует:

- model artifact;
- preprocessing;
- endpoint;
- интеграцию с Telegram;
- конфиги;
- threshold policy;
- логирование;
- monitoring;
- rollback;
- smoke test;
- права доступа;
- обработку ошибок.

Сам алгоритм может быть простым, но production-интеграция содержит высокую неопределённость.

## Почему анализ ошибок — один день

Time box можно ограничить:

- выгрузить False Positive;
- выгрузить False Negative;
- посмотреть top-N;
- сгруппировать причины;
- сформулировать гипотезы.

Не нужно за один день понять все возможные типы спама.

## Почему бустинг — один день

Минимальный эксперимент:

- тот же датасет;
- тот же split;
- базовые параметры;
- тот же расчёт метрики;
- сравнение с логистической регрессией.

Если прироста нет, time box заканчивается. Команда не тратит всю неделю на бесконечный тюнинг Could Have-задачи.

---

# 9. Сценарии изменения плана

## A. Деплой занял четыре дня

```text
Пн–Чт → деплой
Пт    → анализ ошибок
```

Бустинг переносится.

## B. Деплой занял пять дней

```text
Пн–Пт → деплой
```

Анализ ошибок и бустинг переносятся.

## C. Деплой не завершён даже за неделю

Нужно провести разбор:

- какая подзадача была неизвестна;
- какая зависимость не учтена;
- почему задача не была разбита;
- можно ли сделать меньший deployment slice;
- нужен ли spike перед следующим планированием.

## D. Деплой занял два дня

```text
Пн–Вт → деплой
Ср    → анализ ошибок
Чт–Пт → бустинг и дополнительные гипотезы
```

## E. Деплой быстрее, но анализ ошибок занял два дня

```text
Пн–Вт → деплой
Ср–Чт → анализ ошибок
Пт    → бустинг
```

План всё ещё помещается.

---

# 10. Почему нельзя автоматически начинать Should раньше Must

Представим:

```text
Must: production deployment
Should: error analysis
```

Анализ ошибок может быть интереснее и понятнее, поэтому команда начинает с него. Затем выясняется, что для deployment нужны новые права, интеграционные тесты и помощь другой команды.

В результате главный результат не успевают доставить.

Базовое правило:

```text
сначала закрываем обязательное,
затем используем оставшееся время на улучшения.
```

Исключения возможны, если:

- задачи выполняют независимые люди;
- Should снимает блокер Must;
- Must временно заблокирован внешней командой;
- параллельная работа не увеличивает риск.

---

# 11. Зависимости важнее названия категории

Если задача необходима для завершения Must, она сама становится Must.

Пример неправильной классификации:

```text
Must: провести A/B-тест
Should: добавить логирование экспериментальной группы
```

Без логирования тест нельзя измерить. Значит, логирование — обязательная зависимость и тоже Must.

Проверочный вопрос:

> Без какой задачи невозможно закончить текущее Must Have?

---

# 12. MoSCoW не заменяет декомпозицию

Плохая задача:

```text
Задеплоить модель.
```

Хорошая декомпозиция:

1. собрать artifact;
2. реализовать preprocessing;
3. создать endpoint;
4. интегрировать с источником событий;
5. добавить threshold policy;
6. добавить logging;
7. провести smoke test;
8. настроить rollback;
9. включить monitoring;
10. запустить canary.

После декомпозиции оценка становится реалистичнее, а риски — видимыми.

# 13. Практический алгоритм недельного планирования

## Шаг 1. Зафиксировать недельную цель

Пример:

```text
К концу недели антиспам-модель безопасно обрабатывает реальные сообщения.
```

## Шаг 2. Определить Must

Только то, без чего цель нельзя считать достигнутой.

## Шаг 3. Проверить объём Must

Must должен занимать около 60% доступного бюджета. Если он занимает 100%:

- уменьшить scope;
- разбить релиз;
- перенести часть функциональности;
- пересогласовать срок;
- добавить людей только при реальной параллелизации.

## Шаг 4. Определить Should

Высокоценные задачи, которыми можно пожертвовать при задержке.

## Шаг 5. Определить Could

Эксперименты и улучшения, которые переносятся первыми.

## Шаг 6. Явно записать Won't

Это защищает команду от scope creep посреди недели.

## Шаг 7. Каждый день пересчитывать remaining estimate

Полезный вопрос:

```text
Сколько времени, по текущим знаниям, осталось до готовности?
```

Он полезнее, чем абстрактное «готово на 80%».

---

# 14. Пример из финтеха

Недельная цель:

```text
Ввести правило для подозрительных переводов.
```

Must:

- реализовать правило;
- проверить False Positive;
- добавить rollback.

Should:

- dashboard для fraud-аналитиков.

Could:

- автоматический подбор threshold.

Won't:

- Transformer для всех транзакций.

---

# 15. Пример из маркетплейса

Недельная цель:

```text
Не показывать недоступные товары в рекомендациях.
```

Must:

- online availability filter;
- integration test;
- monitoring пустых слотов.

Should:

- анализ влияния на CTR.

Could:

- новый ranking feature.

Won't:

- полная замена recommender architecture.

---

# 16. Пример из forecasting

Недельная цель:

```text
Исправить прогноз для промо-товаров.
```

Must:

- найти ошибку promo flag;
- исправить pipeline;
- пересчитать прогноз.

Should:

- сравнить Accuracy и Bias до и после.

Could:

- попробовать новую модель.

Won't:

- переписывать всю forecasting-платформу.

---

# 17. Главная идея

Правило 60–20–20 — не математический закон. Это практический способ:

- не обещать 100% времени;
- оставить запас;
- пережить ошибку оценки;
- защитить главную цель;
- сохранить фокус;
- управлять неопределённостью.

Короткая формула:

```text
Must   → обещаем
Should → стараемся сделать
Could  → делаем при наличии времени
Won't  → сознательно исключаем
```
