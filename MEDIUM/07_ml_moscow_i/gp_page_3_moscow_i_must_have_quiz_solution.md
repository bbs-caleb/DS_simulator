# 3. Почему выбрано три задачи

Условие:

```text
каждая задача занимает один день
```

Пятидневная неделя и правило 60–20–20:

```text
5 × 60% = 3 дня Must Have
```

Выбранные задачи образуют минимальный полный цикл:

```text
Measure → Fix → Validate
```

То есть:

```text
измерить масштаб
→ исправить проблему
→ проверить эффект
```

---

# 4. Почему анализ доли — Must Have

Нужно получить baseline:

```text
SelfRecommendationRate до исправления
```

Без baseline невозможно ответить:

- насколько проблема массовая;
- какие категории затронуты;
- где искать root cause;
- насколько успешно сработал hotfix;
- каков потенциальный бизнес-эффект.

Метрика:

\[
SelfRecommendationRate =
\frac{\text{показы, где current item попал в рекомендации}}
{\text{все показы recommendation block}}
\]

---

# 5. Почему hotfix — Must Have

Это самый короткий путь к устранению дефекта.

Бизнес-правило:

```text
current item не должен находиться
в final recommendation list для самого себя.
```

Простейшая логика:

```python
recommended_items = [
    item
    for item in recommended_items
    if item != current_item
]
```

В production нужно дополнительно:

- сравнивать согласованные идентификаторы;
- удалять все совпадения;
- обрабатывать variants;
- брать следующего кандидата;
- сохранять четыре карточки, если это возможно.

Hotfix гарантирует отсутствие self-item на уровне final output, независимо от того, почему модель его сгенерировала.

---

# 6. Почему A/B-тест — Must Have

Фильтр изменяет состав recommendation block. Освободившийся слот заполняется другим товаром.

Нужно проверить:

- исчезла ли техническая ошибка;
- вырос ли CTR;
- изменился ли add-to-cart;
- изменился ли GMV;
- не выросла ли latency;
- не появились ли пустые слоты;
- не ухудшилась ли relevance.

В условии указано, что A/B-платформа уже существует и тесты быстрые. Поэтому валидация недорогая и реалистичная.

---

# 7. Почему pipeline не Must Have

Исключение self-pairs из training data может быть полезным root-cause fix.

Но оно требует:

```text
изменить pipeline
→ пересчитать данные
→ обучить модель
→ оценить модель
→ задеплоить модель
```

Кроме того, self-item может появляться не только из train data, но и из:

- fallback;
- cache;
- merge candidate sources;
- неправильного mapping ID;
- post-processing bug.

Поэтому deterministic serving filter быстрее и надёжнее для текущей недели.

---

# 8. Почему diversity-механизм не Must Have

Diversity — более широкая задача.

Она отвечает на вопрос:

> Насколько разные товары представлены внутри выдачи?

Текущая проблема уже конкретна:

```text
current item повторяется в рекомендациях
```

Для неё не нужно сначала проектировать общий diversity score. Это полезное последующее улучшение или monitoring, но не обязательный hotfix.

---

# 9. Почему user-to-item не Must Have

Это полная смена постановки:

```text
item-to-item → рекомендации от текущего товара
user-to-item → рекомендации от истории пользователя
```

Переход потребует:

- user profile;
- новую модель;
- новую data schema;
- новый serving;
- cold-start;
- privacy checks;
- новую evaluation.

Менять весь класс рекомендательной системы ради простого self-filter — overengineering.

---

# 10. Почему широкий error analysis не Must Have

Проблема уже известна и формализована:

```text
current_item_id == recommended_item_id
```

Нужен точечный анализ частоты и источника ошибки, а не детальное исследование всех слабостей модели.

Широкий error analysis можно провести позже, но для текущего hotfix он не является обязательной зависимостью.

---

# 11. Почему кастдев не Must Have

Пользовательская проблема очевидна:

- человек уже смотрит товар;
- блок снова предлагает этот же товар;
- один из четырёх слотов бесполезен.

Не требуется интервью, чтобы понять, что этот слот нужно освободить.

Кастдев полезен для общей стратегии рекомендаций, но не для исправления конкретного deterministic bug.

---

# 12. Почему новая модель не Must Have

Переобучение на исправленном датасете может быть полезно после hotfix, но не нужно для немедленного решения.

Даже новая модель не гарантирует, что current item никогда не появится в final list. Поэтому serving guardrail всё равно нужен.

---

# 13. Почему модель-антагонист не Must Have

Наличие текущего товара и дублей проверяется точным правилом:

```python
current_item in recommended_items
```

или:

```python
len(items) != len(set(items))
```

Обучать ML-модель для проверки точного равенства — неоправданное усложнение.

ML нужен, когда нет точного детерминированного правила. Здесь правило известно.
