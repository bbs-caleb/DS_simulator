# MOSCOW I — страница 2
# Официальный разбор первой задачи и исправление ответа

## 1. Важное исправление

В предыдущем комплекте для страницы 1 была дана неверная приоритизация.

После предоставленного официального разбора правильное распределение такое:

| Действие | Правильная категория MoSCoW |
|---|---|
| Катить текущую модель в прод | **Must Have** |
| Провести анализ ошибок | **Should Have** |
| Попробовать градиентный бустинг | **Could Have** |
| Обучить BERT | **Won't Have** |

Правильный ответ первой задачи:

```text
Анализ ошибок        → Should Have
Обучить BERT         → Won't Have
Катить в прод        → Must Have
Градиентный бустинг  → Could Have
```

---

# 2. Почему прежняя логика была неверной

Прежнее решение слишком формально трактовало критерий:

```text
Recall должен быть выше 90%
```

Фактический результат модели:

```text
Recall = 88.7%
Specificity = 99.6%
```

Из недобора Recall был сделан вывод, что модель нельзя запускать. Но официальный разбор предлагает смотреть не только на буквальное число в старом документе, а на новую информацию о продукте, рисках и стоимости задержки.

Разница с ориентиром составляет:

```text
90.0% - 88.7% = 1.3 процентного пункта
```

При этом ограничение, защищающее обычных пользователей от ошибочного удаления сообщений, уже выполнено:

```text
Specificity = 99.6% > 99.5%
```

То есть наиболее чувствительный риск уже находится в допустимой зоне, а модель способна немедленно сократить объём спама и ручную работу модераторов.

---

# 3. Design document is a living thing

Фраза означает:

> Дизайн-документ — это рабочий документ, который обновляется по мере появления новых данных.

До эксперимента команда могла поставить Recall 90% экспертно или приблизительно. После эксперимента стало видно, что модель с Recall 88.7% уже:

- обнаруживает большую часть спама;
- выполняет жёсткое ограничение по Specificity;
- может резко уменьшить ручную нагрузку;
- реагирует быстрее человека;
- создаёт ценность уже сейчас.

Это не означает, что любые требования можно игнорировать. Нужно отличать:

## 3.1. Жёсткие ограничения

Их нельзя просто пересмотреть без отдельного решения:

- закон;
- безопасность;
- privacy;
- обязательный SLA;
- ограничение инфраструктуры;
- финансовый лимит риска;
- недопустимое число ложных блокировок.

## 3.2. Предварительные ориентиры

Их можно уточнять после эксперимента:

- желаемый Recall;
- ожидаемый uplift;
- примерный latency target;
- предварительный объём данных;
- первоначальная оценка ресурсов.

Зрелая команда не поклоняется числу, записанному до получения данных. Она пересматривает решение осознанно и документирует причины.

# 4. Почему деплой — Must Have

Ключевой проверочный вопрос MoSCoW:

> Что произойдёт, если за неделю команда успеет сделать только эту задачу?

Если команда успеет только задеплоить модель:

- пользователи начнут видеть меньше спама;
- модераторы будут обрабатывать меньше сообщений;
- спам будет удаляться быстрее;
- продукт начнёт создавать реальную ценность;
- появятся production-данные;
- можно будет наблюдать реальные ошибки и drift.

То есть даже единственная выполненная задача уже улучшает жизнь пользователя.

## 4.1. Насколько полезен Recall 88.7%

Из 1000 реальных спам-сообщений модель приблизительно:

```text
887 найдёт;
113 пропустит.
```

Она не идеальна, но без неё модератор должен проверять все 1000 случаев. С ней объём необнаруженного спама становится примерно в девять раз меньше исходного.

## 4.2. Почему скорость реакции тоже создаёт ценность

Автоматический бот:

- работает круглосуточно;
- не спит;
- не устаёт;
- реагирует почти мгновенно;
- масштабируется на большой поток.

Человек-модератор может увидеть спам через минуты или часы. Даже при одинаковом Recall бот уменьшает время, в течение которого вредное сообщение доступно пользователям.

# 5. Почему Specificity особенно важна

False Positive в антиспаме означает:

```text
обычное сообщение
→ ошибочно признано спамом
→ удалено или пользователь наказан
```

Specificity считается так:

\[
Specificity = \frac{TN}{TN + FP}
\]

При Specificity 99.6% из 1000 обычных сообщений примерно:

```text
996 будут оставлены правильно;
4 могут быть ошибочно удалены.
```

Целевое ограничение было не более пяти ошибок на 1000 нормальных сообщений. Модель его выполняет.

Поэтому ситуация выглядит так:

- критический пользовательский риск контролируется;
- Recall чуть ниже первоначального ориентира;
- чистая продуктовая ценность уже положительна.

---

# 6. Почему анализ ошибок — Should Have

Анализ ошибок важен. Он помогает:

- найти основные типы False Negative;
- найти причины False Positive;
- обнаружить ошибки разметки;
- увидеть слабые сегменты;
- понять, каких признаков не хватает;
- выбрать следующий алгоритм;
- подготовить переиспользуемый диагностический код.

Но если команда только проанализировала ошибки, пользователь пока не получил улучшение.

Поэтому порядок такой:

```text
Must Have   → доставить уже доступную ценность;
Should Have → понять, как сделать её ещё больше.
```

Анализ ошибок не становится неважным. Он просто идёт после деплоя.

---

# 7. Почему градиентный бустинг — Could Have

Градиентный бустинг потенциально полезен, потому что умеет находить:

- нелинейности;
- взаимодействия признаков;
- пороговые эффекты;
- сложные комбинации бинарных сигналов.

Например:

```text
есть ссылка
AND аккаунт новый
AND сообщение короткое
AND присутствует слово про доход
```

Однако большинство признаков уже бинарные и имеют понятное направление. Логистическая регрессия может достаточно хорошо назначить им веса. Бустинг не гарантирует прирост без новых признаков и дополнительного тюнинга.

Если команда успеет деплой и анализ ошибок — бустинг стоит попробовать. Если времени не хватит, продукт всё равно получил основную ценность.

Поэтому:

```text
градиентный бустинг → Could Have
```

---

# 8. Почему BERT — Won't Have

BERT может улучшить понимание текста, но в текущем цикле он:

- дорогой;
- медленный;
- требует нового pipeline;
- требует больше памяти;
- может потребовать GPU;
- усложняет inference;
- удлиняет цикл эксперимента;
- ухудшает гибкость добавления нетекстовых признаков.

Спамеры ещё и намеренно искажают слова:

```text
заработок
зapaбoтoк
з@работок
з а р а б о т о к
зара6оток
```

Стандартный tokenizer может работать хуже, поэтому могут понадобиться нормализация, кастомная токенизация или отдельное дообучение.

Все эти расходы возникают ради небольшого дополнительного улучшения, когда простая модель уже приносит пользу.

Следовательно:

```text
BERT → Won't Have в текущем цикле
```

Won't Have означает «не сейчас», а не «никогда».

---

# 9. Правильный порядок приоритетов

```text
1. Must Have   — задеплоить текущую модель
2. Should Have — провести анализ ошибок
3. Could Have  — попробовать градиентный бустинг
4. Won't Have  — обучать BERT в текущем цикле
```

---

# 10. Главный продуктовый урок

Нужно сравнивать две ценности:

```text
ценность раннего запуска
против
ценности дополнительного улучшения модели
```

Если модель уже:

- решает значимую часть проблемы;
- контролирует критический риск;
- может быть внедрена безопасно;
- помогает пользователям;

то полезная модель в production часто ценнее более качественной модели в ноутбуке.
