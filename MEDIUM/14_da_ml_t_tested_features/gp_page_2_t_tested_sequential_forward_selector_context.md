# Page 2 — T-Tested Sequential Forward Selection: контекст задачи

## 1. Что изменилось относительно page_1

На `page_1` мы уже научились:

1. начинать с пустого набора признаков;
2. по одному добавлять кандидатов;
3. оценивать каждый вариант через cross-validation;
4. выбирать вариант с максимальным средним `R²`;
5. останавливаться, когда среднее качество больше не растёт.

Но здесь есть слабое место.

Допустим:

```text
текущий средний R² = 0.7000
новый средний R²   = 0.7003
```

Формально новое среднее выше.

Однако разница равна всего `0.0003`.

Она может возникнуть из-за:

- конкретного разбиения на фолды;
- случайного шума выборки;
- нестабильности модели;
- нескольких удачных validation-фолдов;
- большого количества проверяемых признаков.

Поэтому на `page_2` вопрос меняется.

Мы больше не спрашиваем только:

> Стало ли среднее значение больше?

Мы спрашиваем:

> Улучшается ли модель на одних и тех же validation-фолдах достаточно последовательно, чтобы считать эффект статистически подтверждённым?

---

## 2. Бизнесовый смысл

### Почему «чуть выше метрика» недостаточно

В production каждый признак может стоить денег.

Например, признак может требовать:

- запроса к платному внешнему API;
- тяжёлого SQL JOIN;
- онлайн-расчёта за десятки миллисекунд;
- отдельного feature pipeline;
- нового SLA;
- хранения персональных данных;
- дополнительного мониторинга;
- поддержки новой команды-владельца.

Если offline `R²` вырос случайно, бизнес получит все издержки и почти никакой пользы.

Поэтому логика page_2 ближе к реальному решению:

```text
добавляем признак не просто при лучшем среднем,
а при устойчивом улучшении на повторяющихся CV-разбиениях.
```

## 3. Индустриальные примеры

### Финтех и антифрод

Новый внешний сигнал может стоить деньги за каждый запрос.

Нужно доказать, что он стабильно улучшает:

- recall при фиксированном false-positive rate;
- предотвращённый fraud loss;
- precision ручной проверки;
- approval rate при контроле риска.

Случайный uplift не оправдывает постоянную стоимость API.

### Кредитный скоринг

Новый признак бюро может:

- повышать качество;
- ухудшать fairness;
- увеличивать latency;
- иметь regulatory constraints.

Нужна не только средняя метрика, но и устойчивость результата.

### Маркетплейс

Feature seller reliability может улучшить ranking или ETA prediction.

Но его расчёт может потребовать тяжёлой агрегации по заказам. Добавление оправдано только при устойчивом дополнительном качестве.

### E-commerce

Новый promo-feature может чуть повысить forecast accuracy на одной неделе и не работать на другой.

Повторная CV и статистическая проверка помогают не принять случайный сезонный шум за универсальный сигнал.

### Dating

Новые поведенческие сигналы могут затрагивать privacy. Даже небольшой случайный uplift не оправдывает дополнительный риск сбора данных.

### iGaming и casino

При моделях responsible gaming, AML или fraud нельзя выбирать признаки только по случайному приросту offline-метрики. Ошибка может влиять на реальных пользователей и регуляторные обязательства.

### Crypto

On-chain признаки могут быть нестабильными между market regimes. Устойчивость по фолдам важнее одного удачного среднего значения.

### Big Tech

Для Google, Meta, Anthropic и других больших систем дополнительный feature может влиять на:

- p95 latency;
- стоимость inference;
- объём feature store;
- privacy;
- reliability;
- стоимость retraining.

### Промышленность и Space

Новый сенсор или телеметрический канал — физическая и инфраструктурная стоимость. Признак должен давать подтверждённую диагностическую или прогностическую ценность.

## 4. Почему сравниваются массивы CV scores

При `RepeatedKFold(3 × 10)` получаем:

```text
3 фолда × 10 повторов = 30 значений R²
```

Для текущего набора:

```python
current_scores = [
    current_fold_1,
    current_fold_2,
    ...
    current_fold_30,
]
```

Для набора с кандидатом:

```python
candidate_scores = [
    candidate_fold_1,
    candidate_fold_2,
    ...
    candidate_fold_30,
]
```

Ключевой момент:

```text
current_fold_1 и candidate_fold_1
получены на одном и том же разбиении.
```

Поэтому наблюдения связаны попарно.

---

## 5. Почему нужен `ttest_rel`

`ttest_rel` предназначен для двух связанных наборов измерений.

В этой задаче пары образуются естественно:

```text
качество до добавления признака на fold 1
качество после добавления признака на fold 1
```

Затем:

```text
fold 2 до ↔ fold 2 после
fold 3 до ↔ fold 3 после
...
```

Фактически тест анализирует разности:

```python
candidate_scores - current_scores
```

---

## 6. Гипотезы

Для кандидата проверяются:

### Нулевая гипотеза H0

```text
Новый набор не лучше текущего набора.
```

### Альтернативная гипотеза H1

```text
Новый набор имеет более высокий средний CV score.
```

В коде:

```python
ttest_rel(
    candidate_scores,
    current_scores,
    alternative="greater",
)
```

`greater` относится к первому аргументу:

```text
mean(candidate_scores) > mean(current_scores)
```

---

## 7. Что такое `alpha`

`alpha` — допустимый уровень ошибки I рода.

По умолчанию:

```python
alpha = 0.05
```

Условие принятия кандидата:

```python
p_value < self.alpha
```

Интуитивно:

> Если бы реального улучшения не было, вероятность увидеть настолько выраженный результат должна быть достаточно маленькой.

Важно:

```text
p-value не является вероятностью того, что H0 истинна.
```

---

## 8. Почему нужен `DummyRegressor`

На первой итерации текущего набора признаков ещё нет.

Но t-тесту нужны два массива:

```text
current_scores
candidate_scores
```

Поэтому начальное качество задаётся baseline-моделью:

```python
DummyRegressor()
```

Для регрессии она обычно предсказывает константу, связанную со средним таргетом.

Первый реальный признак сравнивается не с `-∞`, а с понятным baseline.

## 9. Полный алгоритм

```text
1. included_features = []
2. excluded_features = все индексы
3. current_scores = CV scores DummyRegressor

4. Повторить не более max_features раз:

   4.1. significant_candidates = []

   4.2. Для каждого ещё не выбранного признака:

        subset = included_features + [candidate]

        candidate_scores =
            CV scores модели на subset

        p_value =
            paired one-sided t-test(
                candidate_scores,
                current_scores
            )

        если p_value < alpha:
            сохранить кандидата

   4.3. Если значимых кандидатов нет:
        остановиться

   4.4. Среди значимых кандидатов выбрать
        максимальный mean(candidate_scores)

   4.5. Добавить победителя

   4.6. current_scores = scores победителя

5. Отсортировать выбранные индексы
```

## 10. Почему сначала фильтруем по p-value, затем выбираем по mean

На одной итерации несколько кандидатов могут оказаться значимыми.

Например:

| Feature | Mean R² | p-value |
|---:|---:|---:|
| 7 | 0.710 | 0.001 |
| 12 | 0.715 | 0.010 |
| 18 | 0.708 | 0.020 |

При `alpha=0.05` все три значимы.

SFS должен выбрать только один признак.

Поэтому среди прошедших статистический фильтр выбирается максимальный mean `R²`.

---

## 11. Почему нельзя оставить старую проверку `best_score > current_score`

Она сравнивает только два числа:

```text
одно среднее с другим средним
```

Она не учитывает:

- разброс по фолдам;
- число CV-наблюдений;
- последовательность улучшений;
- нестабильность эффекта.

Page_2 требует именно статистическое сравнение массивов.

## 12. Почему прошлый файл получил 0%

Ошибка:

```text
SequentialForwardSelector should have attribute alpha
```

означает, что grader остановился на API-проверке.

В прошлом конструкторе было:

```python
def __init__(
    self,
    model,
    cv,
    max_features=10,
    verbose=0,
):
```

Для page_2 требуется:

```python
def __init__(
    self,
    model,
    cv,
    max_features=10,
    verbose=0,
    alpha=0.05,
):
```

И внутри:

```python
self.alpha = alpha
```

Но одного добавления атрибута недостаточно.

`alpha` должен реально использоваться:

```python
if p_value < self.alpha:
```

## 14. Риски метода

### Множественные сравнения

На каждой итерации тестируется много кандидатов.

При 50 признаках выполняется много гипотез, поэтому возрастает риск ложноположительных решений.

Коррекция Bonferroni может появляться на следующем шаге курса. В текущем файле page_2 она не добавляется, потому что grader сейчас явно сигнализирует о параметре `alpha`, а не о параметре коррекции.

### Зависимость CV scores

Оценки repeated CV не являются идеально независимыми, потому что train-наборы частично пересекаются.

В учебной задаче используется обычный paired t-test. В строгом исследовании нужно учитывать ограничения repeated CV.

### Selection bias

Мы выбираем лучший признак среди множества кандидатов. Даже статистический фильтр не делает итоговую оценку полностью unbiased.

### Leakage

T-test не обнаруживает target leakage. Утёкший признак будет выглядеть очень значимым.

Page_2 добавляет не просто новый параметр.

```text
page_1:
лучшее среднее выше текущего

page_2:
улучшение подтверждено односторонним парным t-тестом
и среди значимых кандидатов выбрано лучшее среднее
```
