<a name="1"></a>
## 1. С чего всё начинается: проблема «бот врёт»

Представьте компанию. У неё есть:

- 4 000 страниц документации,
- 12 000 тикетов поддержки,
- 300 внутренних регламентов,
- 80 юридических документов.

Компания хочет бота, который отвечает на вопросы сотрудников и клиентов
по этим документам. Кажется, задача простая: «взяли LLM, дали ей
документы, готово».

Но LLM не может «съесть» 4 000 страниц за раз. У модели есть **контекстное
окно** — ограничение на длину текста, который она видит одновременно.
Даже если окно огромное (200k+ токенов), кормить туда всю базу знаний
на каждый вопрос:

- **дорого** — вы платите за каждый токен;
- **медленно** — задержка растёт линейно;
- **неточно** — модель «тонет» в шуме и теряет нужный факт
  (эффект называется *lost in the middle*).

Поэтому строят **RAG**.

<a name="2"></a>
## 2. Что такое RAG на пальцах

**RAG = Retrieval-Augmented Generation** = «генерация, усиленная поиском».

Аналогия: студент на экзамене со шпаргалкой.

1. Студент слышит вопрос («Что такое амортизация?»).
2. Он **не** перечитывает весь учебник. Он листает шпаргалку и находит
   3–5 нужных абзацев.
3. Читает только их и формулирует ответ.

RAG работает так же:

```
Вопрос пользователя
        │
        ▼
[1] Превратить вопрос в вектор (эмбеддинг)
        │
        ▼
[2] Найти в векторной базе K самых похожих ЧАНКОВ
        │
        ▼
[3] Склеить: "Вот контекст: <чанки>. Ответь на вопрос: <вопрос>"
        │
        ▼
[4] Отправить это в LLM
        │
        ▼
Ответ пользователю
```

**Чанк** — это тот самый «абзац шпаргалки». Единица хранения и поиска.

И вот здесь ключевая мысль:

> 🔑 **Качество RAG сверху ограничено качеством чанков.**
> Если нужный факт разрезан пополам между двумя чанками — ни одна,
> даже самая дорогая, LLM его не соберёт. Она просто не увидит его целиком.

Никакая замена GPT-4 на Claude Opus не починит плохой чанкинг. Это как
пытаться улучшить фотографию, купив более дорогую рамку.

<a name="3"></a>
## 3. Где именно ломается RAG — и почему виноват чанкинг

Разложим RAG на этапы и посмотрим, где теряется качество.

| Этап | Что делаем | Типичная доля потерь качества |
|---|---|---|
| Парсинг документов | PDF → текст | 10–15 % |
| **Чанкинг** | текст → куски | **30–40 %** |
| Эмбеддинги | куски → векторы | 10 % |
| Поиск (retrieval) | вектор → top-K | 20 % |
| Реранкинг | пересортировать top-K | 10 % |
| Генерация | LLM пишет ответ | 10 % |

Цифры условные и зависят от домена, но порядок именно такой:
**чанкинг — самая недооценённая и самая дорогая по последствиям стадия.**

Причина простая: ошибка чанкинга **необратима**. Всё, что произошло
дальше по пайплайну, работает уже с испорченными данными. Ошибку
ретривера можно компенсировать реранкером; ошибку чанкинга — ничем.

<a name="4"></a>
## 4. Три типа поломок чанкинга (с примерами убытков)

### Поломка №1: Разрыв мысли (truncation / split-in-the-middle)

Исходный текст в регламенте банка:

```
Комиссия за международный перевод составляет 1.5 % от суммы,
но не менее 300 рублей. Для клиентов пакета «Премиум»
комиссия не взимается.
```

Режем по 100 символов:

```
ЧАНК 1: "Комиссия за международный перевод составляет 1.5 % от суммы,
         но не менее 300 рублей. Для кли"
ЧАНК 2: "ентов пакета «Премиум» комиссия не взимается."
```

Пользователь-премиум спрашивает: «Какая у меня комиссия за перевод?»
Ретривер находит ЧАНК 1 (он релевантнее по словам «комиссия», «перевод»).
Бот отвечает: **«1.5 %, минимум 300 рублей»**.

**Что произошло с точки зрения бизнеса:**
- Клиент премиум-сегмента получил неверную информацию о своём тарифе.
- Он либо не сделает перевод (потеря выручки), либо сделает и потом
  придёт с претензией (стоимость обращения в поддержку ≈ 150–400 ₽,
  плюс риск жалобы регулятору).
- В РФ/ЕС неверное информирование о тарифах — это потенциальный
  комплаенс-инцидент.

### Поломка №2: Смешение тем (topic bleeding)

```
ЧАНК: "...ставка по вкладу «Накопительный» — 12 % годовых.
       Раздел 4. Порядок закрытия счёта. Для закрытия счёта
       необходимо подать заявление..."
```

Один чанк содержит две несвязанные темы. Его эмбеддинг — «средний»
между двумя смыслами, то есть не похож ни на одну из них.
Такой чанк плохо находится по обоим вопросам.

**Бизнес-эффект:** падает recall — бот отвечает «я не знаю» на вопросы,
ответ на которые в базе есть. Пользователь идёт в живую поддержку.
Деградация метрики **containment rate** (доля обращений, закрытых ботом).

### Поломка №3: Слишком мелкие чанки (context starvation)

```
ЧАНК 1: "Ставка составляет 12 % годовых."
```

Ставка чего? Вклада? Кредита? Ипотеки? Чанк без контекста бесполезен и,
что хуже, **опасен** — LLM может подставить его к неправильному вопросу.

**Бизнес-эффект:** галлюцинации с высокой уверенностью — худший вид
ошибки, потому что пользователь ей верит.

<a name="5"></a>
## 5. Почему semantic chunking, а не «каждые 500 символов»

Сравним подходы.

| Метод | Как режет | Плюсы | Минусы | Когда применять |
|---|---|---|---|---|
| **Fixed-size** | Каждые N символов/токенов | Просто, быстро, предсказуемый размер | Режет посреди слова/мысли | Прототип, черновой baseline |
| **Fixed-size + overlap** | То же, но с нахлёстом 10–20 % | Смягчает разрывы | Дублирование → рост стоимости хранения и шума | Дешёвый продакшн |
| **Recursive character** | По иерархии: `\n\n` → `\n` → `.` → ` ` | Уважает структуру текста | Не понимает смысл, только форму | Хороший дефолт |
| **Document-based** | По Markdown-заголовкам, HTML-тегам | Идеально для структурированных доков | Требует структуры в источнике | Документация, вики |
| **Semantic (наш случай)** | По скачкам смысла между предложениями | Границы совпадают со сменой темы | Дороже: нужно посчитать эмбеддинги на этапе индексации | Неструктурированные тексты: транскрипты, статьи, письма |
| **Agentic** | LLM сама решает, где резать | Максимальное качество | Очень дорого и медленно | Небольшие критичные корпуса (юр., мед.) |

### Главный аргумент за semantic

Fixed-size режет по **форме**. Semantic режет по **содержанию**.

Смена темы в тексте — это физически измеримое событие: эмбеддинги
соседних предложений внезапно расходятся. Мы просто ловим этот момент.

### Главный аргумент против semantic

Он стоит эмбеддингов **на этапе индексации**. Если у вас 4 000 страниц —
это примерно 100 000 предложений → 100 000 вызовов модели эмбеддингов.

Но: это **разовая** стоимость (или редко повторяемая при обновлении базы),
а качество улучшается на **каждом** запросе пользователя навсегда.
Экономически это почти всегда выгодно.

<a name="6"></a>
## 6. Экономика: как посчитать деньги

Вот шаблон расчёта, который можно принести продакту или на интервью.

### Вводные (пример: поддержка среднего e-com)

| Параметр | Значение |
|---|---|
| Обращений в поддержку в месяц | 200 000 |
| Стоимость одного обращения к живому оператору | 120 ₽ |
| Containment rate (закрывает бот) сейчас | 45 % |
| Containment rate после улучшения чанкинга | 55 % |

### Расчёт выгоды

```
Дополнительно закрыто ботом = 200 000 × (0.55 − 0.45) = 20 000 обращений/мес
Экономия                    = 20 000 × 120 ₽ = 2 400 000 ₽/мес
Годовая экономия            ≈ 28.8 млн ₽
```

### Расчёт затрат

```
Предложений в базе знаний:                    ~100 000
Стоимость эмбеддинга (локальная модель):      ~0 (своё железо, 1 GPU-час)
Стоимость эмбеддинга (API, $0.02 / 1M токенов):
   100 000 предложений × ~30 токенов = 3M токенов ≈ $0.06
Переиндексация раз в неделю:                  ≈ $3 / год
Работа инженера на внедрение:                 ~2 недели
```

Вывод: **затраты околонулевые, выгода — десятки миллионов**.
Именно поэтому чанкинг — это первое, что нужно чинить в RAG,
а не «давайте купим модель подороже».

### Как формулировать это на интервью

> «Semantic chunking — это разовая инвестиция в качество данных, которая
> амортизируется на каждом последующем запросе. В отличие от апгрейда LLM,
> она не увеличивает переменные издержки — только фиксированные,
> и то незначительно.»

<a name="7"></a>
## 7. Индустрия: Финтех / банкинг

### Какие задачи решаем

| Задача | Почему чанкинг критичен |
|---|---|
| Бот по тарифам и продуктам | Тариф = связка «условие + исключение». Разрыв → неверная цена клиенту |
| Комплаенс-ассистент (AML/KYC) | Регламенты — длинные списки условий. Потеря одного пункта = регуляторный риск |
| Разбор договоров | Пункт договора должен быть целым, иначе меняется юридический смысл |
| Внутренний ассистент по 115-ФЗ / PSD2 / GDPR | Нормативка = «требование + оговорка + срок». Всё в одном чанке или никак |
| Анализ звонков (транскрипты) | У транскрипта нет абзацев — только semantic chunking работает |

### Мышление финтех-специалиста

Ключевое слово — **асимметрия ошибок**.

В финтехе неверный ответ стоит **несопоставимо дороже**, чем отсутствие ответа.
«Я не знаю, уточните у оператора» — приемлемо. «Комиссия 0 %», когда она 1.5 %, —
это претензия, а потенциально и штраф.

Следствие для чанкинга: **лучше чанки крупнее и с запасом контекста**,
чем мелкие и точные. Крупный чанк даёт LLM шанс увидеть оговорку.
В терминах нашей задачи это значит: **выше `threshold`** (реже режем)
и **больше буферы** (сглаживаем шум).

### Метрики, за которые отвечаете

- **Answer accuracy на «золотом» наборе** из 300–500 вопросов, размеченных
  комплаенсом. Целевое — 98 %+ на регуляторных темах.
- **Hallucination rate** — доля ответов с фактом, которого нет в источнике.
- **Citation precision** — доля ответов, где приложенная цитата реально
  подтверждает утверждение.
- **Escalation rate** — доля диалогов, ушедших к человеку.

### Пример из практики (Plata, Revolut-подобные необанки)

У необанков документация меняется еженедельно (новые тарифы, промо).
Пайплайн переиндексации запускается по вебхуку из CMS. Semantic chunking
здесь особенно хорош: он не требует, чтобы контент-менеджер соблюдал
структуру Markdown, — работает по смыслу текста как есть.

<a name="8"></a>
## 8. Индустрия: Маркетплейсы и e-commerce

### Какие задачи решаем

| Задача | Роль чанкинга |
|---|---|
| Поиск по отзывам («тихий ли этот пылесос?») | Отзыв = несколько независимых мыслей. Режем по темам, а не по отзывам |
| Q&A по карточке товара | Описание товара — смесь маркетинга и характеристик |
| Ассистент продавца по правилам площадки | Правила = условие + исключение + санкция |
| Поддержка по возвратам | Политика возврата зависит от категории — нельзя смешивать категории в одном чанке |
| Обогащение карточек из PDF-мануалов | Мануалы плохо структурированы после парсинга |

### Мышление e-com специалиста

Ключевое слово — **масштаб и разнообразие**.

У маркетплейса 50 млн SKU и 500 млн отзывов. Здесь важны две вещи:

1. **Стоимость индексации становится реальной.** 500 млн отзывов × эмбеддинг
   каждого предложения — это уже деньги. Решение: semantic chunking
   применяем выборочно — к длинным текстам (мануалы, описания, длинные
   отзывы), а короткие отзывы берём целиком как один чанк.
2. **Разнородность доменов.** Отзыв на смартфон и отзыв на корм для кошек
   имеют разное распределение расстояний. Глобальный `threshold`
   в перцентилях (а не в абсолютных значениях!) здесь спасает — он
   **самонастраивается** под каждый текст.

> 🔑 Это, кстати, главный практический аргумент в пользу перцентиля
> вместо абсолютного порога: перцентиль автоматически адаптируется
> к «температуре» конкретного документа.

### Метрики

- **Conversion rate** на страницах с Q&A-блоком.
- **Return rate** — если бот правильно отвечает на вопросы о размере /
  совместимости, возвратов меньше. Это прямые деньги: логистика возврата
  на маркетплейсе стоит 200–600 ₽.
- **Search zero-result rate** — доля поисков без результата.
- **Time to first answer** в поддержке.

### Кейс-расчёт

```
Возвратов в месяц:                 400 000
Доля возвратов «не подошёл размер / не та совместимость»: 22 % = 88 000
Снижение за счёт качественного Q&A:  −8 % = 7 040 возвратов
Стоимость обработки возврата:      350 ₽
Экономия:                          2 464 000 ₽ / мес
```

<a name="9"></a>
## 9. Индустрия: Two-sided marketplaces (Uber, Airbnb, Avito, Profi.ru)

### Специфика

У вас **две базы знаний** — для спроса и для предложения. И они конфликтуют.

- Водителю нужны правила про заказы, комиссию, рейтинг, блокировки.
- Пассажиру — про отмены, тарифы, безопасность.

Одна и та же фраза «Отмена заказа» означает разные вещи для двух сторон.

### Роль чанкинга

Чанки должны быть **атомарны по актору**. Если в одном чанке смешаны
абзац для водителя и абзац для пассажира, ретривер начнёт выдавать
водителю правила пассажира. Semantic chunking естественно ловит эту
границу, потому что смена актора = смена лексики = скачок эмбеддинга.

### Мышление специалиста

Ключевое слово — **сегментация до ретривера**.

Правильная архитектура: не один индекс, а несколько, с фильтрацией
по метаданным (`audience = driver | rider`). Semantic chunking даёт
чистые границы, а метаданные — маршрутизацию.

### Метрики

- **Supply-side churn** — водители уходят, когда не понимают правила
  блокировок. Ассистент, который внятно объясняет, снижает отток.
- **Dispute rate** — доля споров между сторонами.
- **Time-to-first-order** для новых поставщиков (насколько быстро
  разобрался в платформе).

<a name="10"></a>
## 10. Индустрия: iGaming / casino

### Задачи

| Задача | Роль чанкинга |
|---|---|
| Бот по правилам бонусов и вейджера | Бонус = «условие + вейджер + исключённые игры + срок». Разрыв = спор с игроком |
| Ответы по лицензиям и юрисдикциям | Правила отличаются по странам — нельзя смешивать юрисдикции в чанке |
| Responsible gambling ассистент | Регуляторно обязательные формулировки должны воспроизводиться точно |
| Поддержка по выводу средств | KYC-требования = длинные цепочки условий |

### Мышление специалиста

Ключевое слово — **регуляторная фрагментация**.

Один и тот же продукт в Мальте, Кюрасао и Онтарио имеет разные правила.
Смешение юрисдикций в одном чанке — это не просто ошибка, это **отзыв
лицензии**.

Практический вывод: semantic chunking здесь дополняется **жёстким
структурным чанкингом сверху** — сначала режем документ по юрисдикциям
(по заголовкам), потом внутри каждой секции — семантически. Это
называется **иерархический чанкинг**.

### Метрики

- **Bonus dispute rate** — споры по бонусам.
- **Support containment**.
- **Compliance audit pass rate**.
- **Withdrawal ticket volume** — тикеты про вывод средств самые дорогие.

## 11. Индустрия: Crypto

### Задачи

- Ассистент по документации протокола / API биржи.
- Разбор whitepaper и tokenomics.
- Ответы по комиссиям сетей и мостам.
- Анализ governance-предложений (DAO).
- Мониторинг новостей и оценка sentiment.

### Мышление специалиста

Ключевое слово — **скорость устаревания**.

В крипте контент протухает за дни. Значит:

1. Пайплайн переиндексации должен быть **инкрементальным** — пересчитываем
   эмбеддинги только для изменившихся документов, а не для всей базы.
2. Чанк обязан нести метаданные `valid_from` / `source_version`,
   иначе бот будет уверенно рассказывать про комиссии годичной давности.

### Специфическая проблема чанкинга

Крипто-документация — это смесь прозы и кода:

```
Чтобы вызвать метод, отправьте POST-запрос:

curl -X POST https://api.example.com/v1/swap \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"from":"ETH","to":"USDC"}'

Ответ содержит поле txHash.
```

Наивный `_split_text` по точкам разорвёт curl-команду (там есть точки
в домене!). Вывод: **перед semantic chunking код надо вынести
в плейсхолдеры**, а после — вернуть. Это стандартный приём для
техдокументации.

### Метрики

- **Developer time-to-first-successful-call** — сколько времени
  разработчику нужно, чтобы сделать первый успешный запрос к API.
- **Docs deflection rate** — сколько вопросов в Discord закрыл бот.
- **Stale answer rate** — доля ответов на основе устаревших данных.

<a name="12"></a>
## 12. Индустрия: Dating

### Задачи

- Модерация: поиск в описаниях профилей запрещённого контента.
- Матчинг по «смысловой» совместимости био-текстов.
- Trust & Safety: разбор жалоб и переписок.
- Ассистент по безопасности («как распознать скам»).

### Роль чанкинга

Здесь тексты **короткие** — био на 200 символов. Semantic chunking
для них избыточен. Но он критичен для:

1. **Переписок** (диалоги при разборе жалоб): диалог — это поток
   без структуры, смена темы = смена риска.
2. **Внутренних политик модерации**: они огромны и полны исключений.

### Мышление специалиста

Ключевое слово — **чувствительность и приватность**.

- Персональные данные нельзя гонять через внешний API эмбеддингов →
  используем локальную модель (как `TaylorAI/bge-micro-v2` в нашей задаче —
  она специально маленькая, чтобы крутиться на CPU).
- Ошибка модерации в обе стороны дорога: пропустили скам — потеря доверия
  и репутационный риск; забанили невиновного — отток.

### Метрики

- **Precision / Recall модерации**.
- **Report-to-action time**.
- **False-ban rate**.
- **Match-to-conversation rate**.

<a name="13"></a>
## 13. Индустрия: BigTech

### Google / Meta

Масштаб: миллиарды документов. Здесь semantic chunking в наивном виде
не применяют — слишком дорого считать эмбеддинги на каждое предложение
всего веба. Применяют:

- **каскад**: дешёвый структурный чанкинг на всём корпусе → semantic
  только на top-N документах, отобранных первым этапом;
- **обучаемые модели границ** — вместо перцентиля от расстояний
  используется отдельная маленькая модель, предсказывающая
  «здесь граница темы».

Задача, которую решают: **passage retrieval** — найти не документ,
а конкретный пассаж, отвечающий на запрос.

### Anthropic

Публично известный подход — **contextual retrieval**: перед
эмбеддингом каждого чанка LLM дописывает к нему короткое описание
контекста («Этот фрагмент из отчёта ACME за Q2 2023, раздел про выручку»).
Это резко снижает долю неудачных извлечений.

Мышление: **чанк не должен зависеть от соседей, чтобы быть понятным**.
Semantic chunking решает ту же проблему структурно, contextual
retrieval — через обогащение. В проде их комбинируют.

### SpaceX / аэрокосмос / BP / промышленность

Задача: ассистент по инженерной документации, регламентам ТО,
протоколам безопасности.

Специфика:
- Документы — сотни тысяч страниц PDF, часто сканы → нужен OCR,
  после которого структура теряется полностью. **Semantic chunking
  становится единственным вариантом**, потому что заголовков в тексте
  после OCR уже нет.
- Цена ошибки максимальна: неверная инструкция по регламенту —
  это инцидент на производстве.
- Требование к **traceability**: каждый ответ должен ссылаться
  на конкретный документ, страницу и абзац. Значит, чанк должен
  нести метаданные о своём происхождении.

### Plata (и вообще финтех-стартапы)

Мышление: **скорость выхода на рынок**. Здесь semantic chunking
привлекателен тем, что не требует ручной разметки структуры документов —
взял тексты как есть, получил приемлемое качество за день.

<a name="14"></a>
## 14. Метрики, которые реально спросят

### Метрики качества чанкинга (offline, без пользователей)

| Метрика | Что измеряет | Как считать |
|---|---|---|
| **Chunk coherence** | Насколько чанк «про одно» | Средняя внутричанковая косинусная близость предложений |
| **Chunk separation** | Насколько соседние чанки различны | Косинусное расстояние между эмбеддингами соседних чанков |
| **Boundary F1** | Совпадение с разметкой человека | Сравнить предсказанные границы с эталонными |
| **Chunk size distribution** | Нет ли «монстров» и «крошек» | Гистограмма длин; смотрим p5 / p50 / p95 |

### Метрики ретривера (offline, с размеченным набором)

| Метрика | Смысл |
|---|---|
| **Recall@K** | В скольких % случаев нужный чанк попал в топ-K |
| **MRR** | Насколько высоко в списке стоит правильный чанк |
| **nDCG@K** | То же, но с учётом градаций релевантности |
| **Context precision** | Доля реально полезных чанков среди переданных в LLM |

> Recall@K — главная метрика для RAG. Логика: если нужного чанка нет
> в контексте, LLM физически не может ответить правильно.
> Всё остальное — оптимизация уже поверх этого потолка.

### Продуктовые метрики (online)

| Метрика | Смысл |
|---|---|
| **Containment / Deflection rate** | Доля обращений, закрытых без человека |
| **CSAT / Thumbs-up rate** | Удовлетворённость ответом |
| **Escalation rate** | Доля эскалаций к оператору |
| **Hallucination rate** | Доля ответов с выдуманными фактами (ручной аудит выборки) |
| **Cost per resolved ticket** | Стоимость решённого обращения |
| **p95 latency** | Задержка ответа |

<a name="15"></a>
## 15. Когда semantic chunking НЕ нужен

Это важный вопрос на интервью — умение сказать «не надо» ценится выше,
чем умение всё усложнить.

**Не нужен, если:**

1. **Документы хорошо структурированы.** Markdown с заголовками, HTML
   с секциями, JSON — режьте по структуре, это точнее и бесплатно.
2. **Тексты короткие.** Отзыв на 300 символов, твит, био — это уже чанк.
3. **Тексты однородные по теме.** Карточка товара про один товар —
   резать по смыслу нечего.
4. **Латентность индексации критична.** Если документы должны быть
   доступны через 100 мс после загрузки, считать эмбеддинги некогда.
5. **Домен требует детерминизма.** Юридические документы иногда обязаны
   резаться строго по пунктам — «пункт 4.2.1 целиком» и никак иначе.
6. **Бюджет на индексацию нулевой** и корпус огромный.

**Компромисс, который стоит предложить:** гибрид.

```
1) Режем документ по структуре (заголовки, разделы)  ← дёшево, надёжно
2) Секции длиннее N токенов — дорезаем семантически  ← дорого, но редко
3) Секции короче M токенов — склеиваем с соседними   ← убираем «крошки»
```

Это то, что реально стоит в продакшене у большинства команд.

<a name="16"></a>
## 16. Словарь терминов

| Термин | Простыми словами |
|---|---|
| **Эмбеддинг** | Список чисел (вектор), представляющий смысл текста. Похожие по смыслу тексты → близкие векторы |
| **Косинусное расстояние** | Мера непохожести двух векторов. 0 = одинаковые, 1 = не связаны, 2 = противоположны |
| **Чанк (chunk)** | Кусок текста — единица хранения и поиска в RAG |
| **RAG** | Поиск релевантных кусков + генерация ответа по ним |
| **Retriever (ретривер)** | Компонент, который ищет чанки по запросу |
| **Reranker** | Модель, которая пересортировывает найденные чанки точнее |
| **Векторная база** | Хранилище эмбеддингов с быстрым поиском ближайших (FAISS, Qdrant, pgvector, Pinecone) |
| **Контекстное окно** | Максимум текста, который LLM видит за раз |
| **Токен** | Кусочек слова; единица, которой измеряют длину для LLM |
| **Перцентиль** | Значение, ниже которого лежит заданный % данных. p90 = «90 % значений меньше» |
| **Containment rate** | Доля обращений, закрытых ботом без человека |
| **Recall@K** | Доля запросов, где правильный чанк попал в топ-K результатов |
| **Галлюцинация** | Выдуманный моделью факт, поданный как достоверный |
| **Hierarchical chunking** | Сначала по структуре, потом внутри — по смыслу |
| **Contextual retrieval** | Дописывание контекста к чанку перед эмбеддингом |

## Итог: три тезиса, которые надо запомнить

1. **Чанкинг — это потолок качества RAG.** Всё, что вы сделаете дальше
   по пайплайну, ограничено тем, насколько целыми остались мысли.
2. **Semantic chunking режет по смыслу, а не по форме.** Он ловит
   момент, когда эмбеддинги соседних предложений внезапно расходятся.
3. **Перцентильный порог — это самонастройка.** Он адаптируется
   к «температуре» каждого конкретного документа, поэтому один и тот же
   параметр работает и на юридическом тексте, и на транскрипте звонка.
