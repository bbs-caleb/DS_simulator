### 1.2. Аргумент №1: градиенты

Вспомни, как учится модель (из разбора первой страницы):

1. модель делает предсказание;
2. считаем loss — насколько плохо;
3. **считаем градиент loss'а по всем параметрам модели** — то есть в какую сторону крутить каждый из миллионов весов;
4. делаем шаг.

Шаг 3 — это и есть **обратное распространение ошибки (backpropagation)**.

**Что это значит в numpy.** Numpy умеет только считать числа вперёд. Он не знает, откуда взялся массив и какая формула его породила. Значит, чтобы получить градиент, нужно **вручную вывести производную** всей цепочки — от loss'а через каждый слой сети до самого первого веса — и запрограммировать её отдельной функцией.

Для нашей формулы производная выглядит так (это ещё простой случай):

$$
\frac{\partial L}{\partial x_1} =
\begin{cases}
2(x_1 - x_2), & y = 1 \\[6pt]
-2\big(margin - D\big)\dfrac{x_1 - x_2}{D}, & y = 0,\ D < margin \\[6pt]
0, & y = 0,\ D \ge margin
\end{cases}
$$

А теперь представь, что перед этим loss'ом стоит ResNet-50 из 50 слоёв. Производную нужно вывести **через все 50 слоёв**. Вручную. И заново — при каждом изменении архитектуры.

**Это неосуществимо на практике.** Именно поэтому существуют DL-фреймворки.

**Что делает PyTorch.** Из текста урока:

> Удобство pytorch заключается в том, что он умеет автоматически считать градиенты.

PyTorch запоминает **каждую операцию**, которую ты применил к тензорам, и строит из них **вычислительный граф**. Когда ты вызываешь `loss.backward()`, он проходит по этому графу назад и по цепному правилу вычисляет все производные сам.

Ты пишешь только **прямой проход** (формулу вперёд). Обратный проход PyTorch выводит автоматически. Этот механизм называется **autograd**.

> 🔑 **Главный практический вывод для этого задания:** твоя функция должна быть написана **только через операции PyTorch над тензорами**. Если ты где-то вытащишь число из тензора (через `.item()`, `float()`, `int()`) или уйдёшь в numpy — **граф разорвётся**, градиенты не посчитаются, и loss станет бесполезен для обучения.
>
> Именно поэтому в шаблоне написано `Returns: torch.Tensor`, а не `float`. В numpy-версии мы возвращали `float`. Здесь — **тензор**. Это принципиальное отличие, и на нём валятся.

### 1.3. Аргумент №2: GPU

Из текста урока:

> Он распространен в индустрии, умеет делать вычисления на GPU и очень похож на numpy функционалом.

**Что такое GPU и почему это важно.** Видеокарта содержит тысячи простых вычислительных ядер (у современных — десятки тысяч), тогда как процессор имеет 8–64 сложных. Для задач, где нужно выполнить одну и ту же простую операцию над миллионами чисел (а обучение нейросети — это ровно оно), GPU быстрее CPU **в 10–100 раз**.

Numpy работает **только на CPU**. Точка. Чтобы использовать GPU, нужны совсем другие инструменты.

PyTorch-тензор переносится на GPU одной строкой:

```python
x = x.to("cuda")
```

и весь дальнейший код работает без изменений.

**Что это значит в деньгах.** Обучение энкодера лиц на CPU — недели. На одной видеокарте — часы. При стоимости аренды GPU-инстанса в облаке разница между «неделя CPU» и «три часа GPU» — это не только деньги, но и скорость итераций команды: сколько гипотез вы успеете проверить за квартал.

### 1.4. Почему PyTorch, а не что-то ещё

| Фреймворк | Статус на 2025–2026 |
|---|---|
| **PyTorch** | Доминирует в исследованиях и всё сильнее в проде. HuggingFace, все SOTA-модели, вся публикационная активность |
| **TensorFlow / Keras** | Легаси в большинстве команд, но много старого прода в BigTech |
| **JAX** | Ниша: научные вычисления, крупные лабы (Google DeepMind, Anthropic) |
| **numpy** | Прототипирование, классический ML, обработка данных — но не обучение DL |

Для собеседования: **PyTorch — это де-факто стандарт**, и если в вакансии написано «Deep Learning», подразумевается он.

### 1.5. Ключевая мысль для интервью

> «Numpy и PyTorch синтаксически похожи, но решают разные задачи. Numpy — это библиотека для вычислений. PyTorch — это система дифференцируемых вычислений: он не просто считает, он запоминает, как считал, и умеет пройти назад. Плюс он даёт GPU. Поэтому прототип можно писать на numpy, а обучать — только на PyTorch.»

### 2.2. 🔴 Главное отличие: возвращаем тензор, а не число

Это ошибка №1 в этом задании у людей, которые только что сдали numpy-версию.

```python
# ❌ НЕПРАВИЛЬНО — сработает по значению, но разорвёт граф
return float(loss.mean())
return loss.mean().item()

# ✅ ПРАВИЛЬНО
return loss.mean()
```

**Почему это критично.** `.item()` и `float()` достают из тензора обычное питоновское число. Обычное число **не помнит**, откуда оно взялось. Граф вычислений обрывается, `loss.backward()` упадёт с ошибкой `element 0 of tensors does not require grad`.

То есть функция, возвращающая `float`, **физически не может использоваться для обучения нейросети** — а это и есть единственная причина её существования.

Грейдер почти наверняка проверяет: (а) тип возврата, (б) наличие `grad_fn` у результата, (в) возможность вызвать `.backward()`.

### 2.3. Словарь соответствий numpy → PyTorch

Полезно держать перед глазами. Из текста урока: «очень похож на numpy функционалом» — это правда, но названия местами другие.

| Numpy | PyTorch | Комментарий |
|---|---|---|
| `np.array([1,2,3])` | `torch.tensor([1,2,3])` | создание |
| `a.shape` | `a.shape` | одинаково |
| `a - b` | `a - b` | одинаково |
| `a.sum(axis=1)` | `a.sum(dim=1)` | **`axis` → `dim`** ⚠️ |
| `np.sqrt(a)` | `torch.sqrt(a)` / `a.sqrt()` | |
| `np.maximum(a, 0)` | `torch.clamp(a, min=0)` | **разные имена!** ⚠️ |
| `np.mean(a)` | `a.mean()` / `torch.mean(a)` | |
| `np.linalg.norm(a, axis=1)` | `torch.linalg.norm(a, dim=1)` | |
| `np.einsum(...)` | `torch.einsum(...)` | одинаково |
| — | `.backward()` | **нет аналога в numpy** |
| — | `.to("cuda")` | **нет аналога в numpy** |
| — | `.grad` | **нет аналога в numpy** |

> ⚠️ **Две ловушки, на которых спотыкаются чаще всего:**
> 1. `axis=` в PyTorch называется `dim=`. Написал `axis=1` → `TypeError`.
> 2. Аналог `np.maximum(a, 0)` в PyTorch — это `torch.clamp(a, min=0)`, а не `torch.maximum`. Функция `torch.maximum` существует, но она сравнивает **два тензора**, а не тензор со скаляром (со скаляром она тоже отработает через broadcasting, но `clamp` — идиоматичнее и быстрее).

### 2.4. Про скорость: 20 баллов

Как и в numpy-версии, **любой цикл `for` по парам убьёт эти баллы**. Всё делается векторизованными операциями над тензорами.

Но есть нюанс: в PyTorch **быстрейший способ считать расстояние отличается от numpy**.

Замеры на 50 000 пар × 512 (CPU, 4 потока, среднее по 8 прогонам):

| Способ | numpy | PyTorch |
|---|---|---|
| `linalg.norm(diff, dim/axis=1)` | 0.159 с | **0.064 с** ⭐ |
| `einsum("ij,ij->i", d, d)` | **0.099 с** ⭐ | 0.121 с |
| `(d*d).sum(dim=1)` | 0.620 с | 0.163 с |
| `d.pow(2).sum(dim=1)` | — | 0.119 с |

**Вывод, который стоит запомнить:** нельзя механически переносить оптимизации между библиотеками. В numpy выигрывает `einsum`, в PyTorch — `torch.linalg.norm` (он вызывает специализированное ядро BLAS для вычисления норм). Разница **в 2 раза** — а это те самые 20 баллов.

### 2.5. Скрытая ловушка: pylint и PyTorch

Есть известная проблема: **pylint выдаёт ложное срабатывание на функции из `torch.linalg`**.

```
E1102: torch.linalg.norm is not callable (not-callable)
```

Это **не ошибка в коде** — код работает идеально. Pylint просто не умеет разбирать динамическую регистрацию функций внутри PyTorch и решает, что `torch.linalg.norm` — не функция.

Но оценка при этом падает с 10.00 до **1.67**, а за качество кода дают 20 баллов. То есть эта мелочь стоит ~17 баллов.

Как решается — разобрано в файле с объяснением кода.

> 💡 Это очень жизненная ситуация: линтер ругается на корректный код из-за особенностей сторонней библиотеки. Умение отличить настоящую ошибку от false positive и грамотно его подавить — обычная часть работы. На код-ревью такие подавления пишут точечно и с пояснением, а не отключают проверку глобально.

## Часть 3. Где это применяется в реальном проде

Чтобы задание не выглядело абстрактным упражнением — вот как та же функция выглядит внутри настоящего цикла обучения:

```python
for epoch in range(num_epochs):
    for x1_batch, x2_batch, y_batch in dataloader:
        x1_batch = x1_batch.to(device)          # переносим на GPU
        x2_batch = x2_batch.to(device)
        y_batch  = y_batch.to(device)

        e1 = encoder(x1_batch)                  # сиамская сеть: одна модель,
        e2 = encoder(x2_batch)                  # два вызова, ОБЩИЕ веса

        loss = contrastive_loss(e1, e2, y_batch, margin=5.0)   # ← наша функция

        optimizer.zero_grad()
        loss.backward()                         # ← autograd проходит назад
        optimizer.step()                        # ← шаг оптимизации
```

Видишь строку `loss.backward()`? Именно ради неё функция обязана возвращать тензор. Если бы она вернула `float`, эта строка упала бы, и всё обучение было бы невозможно.

И обрати внимание на `encoder(x1_batch)` и `encoder(x2_batch)` — **одна и та же переменная `encoder`**. Это и есть сиамская сеть с общими весами, о которой шла речь на прошлой странице.

## Часть 4. Мостик дальше

После Contrastive Loss на numpy и PyTorch логично следует **Triplet Loss** — он в названии урока. Там:

- на вход придут три тензора: `anchor`, `positive`, `negative`;
- меток `y` не будет — роли зашиты в имена аргументов;
- расстояний нужно считать два;
- формула: `max(D(A,P) − D(A,N) + margin, 0)`.

Все инструменты у тебя уже будут: `torch.linalg.norm` для расстояний, `torch.clamp` для отсечения, `.mean()` для усреднения, возврат тензора для autograd.
